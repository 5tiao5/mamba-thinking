# 调用关系参考

这份文档不讲字段细节，而是回答：

**实现某个功能时，应该从哪个入口开始，调用谁，不该绕过谁。**

---

## 1. 总规则

推荐调用顺序：

`FastAPI route -> ProductApiHandlers -> Service -> Repository / Registry / research_agent`

也就是说：

- 前端只调 HTTP API
- route 只做路由
- handler 只收参数、调 service、包响应
- 复杂业务逻辑放 `services/`
- Agent 分析逻辑放 `research_agent/`
- 数据读写放 `repositories/`

不要做的事：

- handler 直接访问 repository
- 前端直接猜测 Agent 内部 state
- 页面逻辑绕过 API 直接依赖 Python 内部结构

## 3. 关键功能调用链

### 3.1 创建会话

接口：

- `POST /conversations`

调用链：

- `fastapi_app.py -> create_conversation`
- `handlers.py -> ProductApiHandlers.create_conversation`
- `ConversationService.create_conversation`
- `ConversationRepository.create`

### 3.2 读写消息

接口：

- `GET /conversations/{conversation_id}/messages`
- `POST /conversations/{conversation_id}/messages`

调用链：

- `handlers.py -> list_messages / create_message`
- `MessageService.list_messages / create_message`
- `MessageRepository.list_by_conversation / create`

### 3.3 继续对话并创建 follow-up task

接口：

- `POST /conversations/continue`

调用链：

- `ProductApiHandlers.continue_conversation`
- `ConversationService.get_conversation`
- `MessageService.create_message`
- `MessageService.get_recent_context`
- `ResearchService.create_follow_up_task`
- `ResearchTaskRepository.create`

当前特点：

- 已经是真实链路
- 但上下文增强还偏轻量

### 3.4 创建研究任务

接口：

- `POST /research/tasks`

调用链：

- `ProductApiHandlers.create_research_task`
- `ResearchService.create_task`
- `ResearchTaskRepository.create`

### 3.5 运行研究任务

接口：

- `POST /research/tasks/{task_id}/run`

调用链：

- `ProductApiHandlers.run_research_task`
- `ResearchService.get_task`
- `ResearchService.run_task`
- `research_agent.pipeline.run_pipeline`
- `workspace_mapper.workspace_from_agent_state`
- `WorkspaceRepository.save`
- `MessageService.create_assistant_message`（成功或失败回写）

### 3.6 读取 workspace

接口：

- `GET /research/tasks/{task_id}/workspace`

调用链：

- `ProductApiHandlers.get_workspace`
- `WorkspaceService.get_workspace_snapshot`
- `WorkspaceRepository.get_by_task`

说明：

- 前端消费的是稳定的 snapshot
- 不应直接消费旧版 Agent state

### 3.7 会话与任务历史

接口：

- `GET /conversations`
- `GET /conversations/{conversation_id}`
- `GET /research/tasks`
- `GET /research/tasks/{task_id}`

调用链：

- `handlers.py -> list_conversations / get_conversation / list_research_tasks / get_research_task`
- `ConversationService / MessageService / ResearchService`
- 对应 repository

### 3.8 tools / skills

接口：

- `GET /tools`
- `PATCH /tools/{tool_id}`
- `GET /skills`
- `POST /skills`
- `PATCH /skills/{skill_id}`
- `DELETE /skills/{skill_id}`

调用链：

- `ProductApiHandlers.list_tools / update_tool / list_skills / create_skill / update_skill / delete_skill`
- `ToolService / SkillService`
- `SkillRepository / SkillRegistry`

## 4. 与 taxonomy / workspace 相关的新调用边界

这是当前最容易被误解的一块。

### taxonomy 不是前端自己算的

当前来源链：

- `research_agent/nodes/taxonomy.py` 生成基础 taxonomy
- `workspace_mapper.py` 组装 workspace
- `taxonomy_grounding_service.py` 负责把 taxonomy 分支重新对齐到真实论文与 gap

所以前端只负责展示，不负责重新判 coverage。

### graph 不是前端自己拼的

当前来源链：

- `research_agent/nodes/evolution.py` 生成关系边
- `workspace_mapper.py` 清洗成前端稳定结构
- `WorkspaceGraphCanvas.tsx` 负责图形展示

## 7. 一句话总结

如果组员忘了该调谁，不要硬猜。

先问自己三件事：

1. 这是前端页面需求还是后端业务需求
2. 这个功能有没有现成 API
3. 这个逻辑应该属于 handler、service、repository，还是 research_agent

这样项目就不会重新变成“谁想到哪写到哪”的状态。
