# 消息链路说明

这份文档只解释一件事：

**从 Conversation 到 Message，再到 follow-up task 和 assistant 回复，当前系统到底怎么走。**

---

## 1. 当前消息链路已经到什么程度

当前已经不是“只能保存用户发过什么”，而是已经具备：

- 创建会话
- 写入用户消息
- 读取消息列表
- 继续追问
- 创建 follow-up task
- 任务完成后回写 assistant message

也就是说：

**消息链路已经从“聊天记录”进化成了“研究会话记录”。**

---

## 2. 当前已经打通的链路

### 2.1 创建会话

入口：

- `POST /conversations`

效果：

- 创建 `Conversation`
- 返回 `conversation_id`

### 2.2 写消息

入口：

- `POST /conversations/{conversation_id}/messages`

效果：

- 在指定会话下创建 `MessageRecord`

### 2.3 读消息

入口：

- `GET /conversations/{conversation_id}/messages`

效果：

- 读取某个 conversation 下的消息列表

### 2.4 继续对话

入口：

- `POST /conversations/continue`

当前已经会做：

1. 校验 `conversation_id`
2. 把用户输入写成一条消息
3. 读取最近上下文，返回 `context_preview`
4. 按需创建一条 follow-up task

### 2.5 回写 assistant 回复

入口：

- 不是单独 API，而是在任务运行后自动发生

当前已经会做：

1. 任务运行成功后，生成一条 assistant message
2. 任务运行失败后，也写入一条失败说明消息

这意味着：

- 对话历史里不再只剩用户追问
- assistant 也开始真正参与会话时间线

---

## 3. 当前核心调用链

### 3.1 继续追问链路

调用顺序：

1. `ConversationService.get_conversation`
2. `MessageService.create_message`
3. `MessageService.get_recent_context`
4. `ResearchService.create_follow_up_task`

也就是说：

- 会话是否存在，由 `ConversationService` 负责
- 用户消息如何写入，由 `MessageService` 负责
- follow-up task 是否创建，由 `ResearchService` 负责

### 3.2 任务完成后的回写链路

调用顺序：

1. `ResearchService.run_task`
2. 成功或失败生成任务结果摘要
3. `MessageService.create_assistant_message`

这样 assistant 消息会和 task 结果建立语义关联。

---

## 4. 当前链路里有哪些对象

### `Conversation`

表示一条长期研究主线。

### `MessageRecord`

表示这条主线上的一条消息。

### `ResearchTask`

表示某次具体分析动作。  
一次 conversation 下可以有多条 task，尤其是多轮追问时。

### `Workspace`

表示某个 task 的分析结果快照。

所以当前的逻辑不是：

- 一个会话只对应一个结果

而是：

- 一个 conversation 下可以有很多 message
- 很多 message 里有些会触发 task
- 每个 task 再产出一个 workspace

---

## 5. 当前真实可用到什么程度

### 已经可用

- 创建会话
- 创建用户消息
- 读取消息列表
- 继续对话时返回 `context_preview`
- 继续对话时创建 follow-up task
- 任务运行后回写 assistant message

### 还没完全做实

- assistant message 还偏“任务摘要风格”
- 多轮对话还没有更强的上下文压缩
- 消息历史目前更像“研究日志”，还没完全变成自然连续问答
- knowledge / RAG 还没有真正增强这条链路

---

## 6. 当前对前端意味着什么

前端当前最适合围绕这条链路做：

- 对话页消息时间线
- 用户追问输入
- task 状态与消息联动展示
- assistant 回答样式优化
- 历史页里按 conversation 展示多轮记录

也就是说：

前端不该只把消息当普通聊天泡泡，而应该把它理解成：

**“持续研究会话的时间线”**

---

## 7. 当前对后端意味着什么

后端下一阶段最值得继续补的是：

1. 让 assistant 回复更像回答，而不是像任务日志
2. 加强 `continue_conversation` 的上下文理解
3. 把 knowledge / RAG 接入这条链
4. 让 message、task、workspace 的关联在接口中更明确

例如后续可以增强：

- `message.metadata.triggered_task_id`
- `message.metadata.workspace_task_id`
- `assistant` 回复中的知识来源说明

---

## 8. 一句话总结

当前消息链路已经从“能记录用户发了什么”升级到了：

**能记录用户追问、能触发新任务、能在任务结束后回写 assistant 结果。**

下一阶段重点不是再从零设计，而是：

**把这条链进一步做成真正自然、可持续、可回看的研究会话链路。**
