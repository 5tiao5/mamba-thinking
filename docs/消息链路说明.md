# 消息链路说明

## 1. 这份文档讲什么

这份文档只解释一件事：

**从会话到消息，再到继续对话和 follow-up task，当前系统到底怎么走。**

---

## 2. 当前已经打通的链路

### 2.1 创建会话

入口：

- `POST /conversations`

效果：

- 创建一条 `Conversation`
- 返回 `conversation_id`

### 2.2 写消息

入口：

- `POST /conversations/{conversation_id}/messages`

效果：

- 在指定会话下创建 `MessageRecord`
- 当前使用 `MessageRepository`

### 2.3 读消息

入口：

- `GET /conversations/{conversation_id}/messages`

效果：

- 按会话读取消息列表

### 2.4 继续对话

入口：

- `POST /conversations/continue`

当前已经会做：

1. 校验 `conversation_id`
2. 把用户输入写成一条消息
3. 读取最近几条上下文，返回 `context_preview`
4. 如果 `create_follow_up_task = true`，创建一条 follow-up task

这意味着现在的“继续对话”不再只是占位接口，而是已经能真正串起“消息 -> 下一轮任务”的链路。

---

## 3. 核心调用链

`continue_conversation`

调用顺序：

1. `ConversationService.get_conversation`
2. `MessageService.create_message`
3. `MessageService.get_recent_context`
4. `ResearchService.create_follow_up_task`

也就是说：

- 会话是否存在，由 `ConversationService` 负责
- 消息创建与上下文预览，由 `MessageService` 负责
- follow-up task 创建，由 `ResearchService` 负责

handler 不直接碰 repository。

---

## 4. 当前数据流里有哪些对象

### `Conversation`

表示一轮长期交互上下文。

### `MessageRecord`

表示一条具体消息。

### `ResearchTask`

表示一次具体分析任务。  
一次对话里可以产生多条任务，尤其是 follow-up task。

---

## 5. 当前真实可用到什么程度

已经可用：

- 创建会话
- 创建消息
- 读取消息列表
- 继续对话时返回 `context_preview`
- 继续对话时创建 follow-up task 记录

还没做实的：

- 更强的上下文摘要压缩
- 自动判断是否立即运行 follow-up task
- 消息分页和更完整的历史查询
- 基于知识库的上下文增强

---

## 6. 前端现在最适合接什么

前端现在最适合围绕这条链路做：

- 对话页消息列表
- 发送消息
- 展示 `context_preview`
- 展示 `follow_up_task`
- 提供“立即运行这条 follow-up task”的按钮

这样做的好处是：

- 能直接联调
- 用户能明显感觉到“多轮对话”在工作
- 不再只是页面占位

---

## 7. 后端下一步最值得补什么

后端下一步最值得继续补的是：

1. 更真实的上下文摘要
2. follow-up task 的自动运行策略
3. 历史消息查询能力
4. shared knowledge / RAG 对 continue conversation 的增强

---

## 8. 一句话总结

当前消息链路已经从“能发消息”升级到了：

**能继续对话，并把追问转成下一轮研究任务。**
