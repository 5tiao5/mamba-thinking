# 主链质量验收说明

更新时间：2026-06-15

这套验收用于判断 Product Agent 是否真的能帮用户完成科研调研，而不是只证明接口能跑通。

## 1. 验收目标

主链质量验收回答四个问题：

1. 用户提出研究主题后，系统是否能找到有用论文。
2. 用户继续追问后，系统是否真的补搜或重排，而不是只复用旧结果。
3. 工作台展示的 taxonomy、图谱、空白和建议是否有证据边界。
4. 本研究总览是否能沉淀多轮研究，而不是简单拼接最新一轮。

这套验收和 [检索质量评测说明](检索质量评测说明.md) 的关系：

- 检索质量评测关注单点搜索质量。
- 主链质量验收关注完整产品体验和多轮研究可信度。

## 2. 全局红线

任何主链用例触发以下情况，都应视为不通过：

| 红线 | 说明 |
| --- | --- |
| 静默 fallback | 检索失败后用 seed 或保底论文伪装成功 |
| 追问不补搜 | 用户明确要求近年、新方向或扩展范围，但系统只从旧论文中重新挑选 |
| 跑题核心论文 | 核心分析池出现明显不属于主题的论文，且没有被标为边缘证据 |
| 假引用数 | 引用数未知时显示 `0`，而不是“未获取” |
| 分支论文丢失 | taxonomy 分支显示有论文，但详情区不展示论文名 |
| 图谱乱连 | 普通主题相似被展示为改进、引用或扩展关系 |
| 结论无证据 | gaps / ideas 没有绑定论文却被包装成已证实结论 |
| RAG 污染 | 共享知识命中直接支撑当前结论，但该资料未进入当前分析论文池 |
| 总览覆盖旧价值 | 最新一轮结果完全挤掉早期高价值论文或结论，且没有解释 |

## 3. 建议验收节奏

每次改动以下模块后，至少跑 2 个主链用例：

- query decomposition
- retrieval plan
- arXiv / Semantic Scholar 查询
- paper relevance
- workspace merge
- graph relationship
- RAG filtering
- PDF import
- Skill selection

答辩前建议完整跑 6 个用例，并记录结果。

## 4. 小而硬用例

结构化用例文件位于：

`evaluation/main_chain_cases.json`

### C1：AI Agent 工具使用评测

首轮主题：

`AI Agent 工具使用的评测方法，重点关注工具选择、函数调用和失败恢复`

追问：

`补充近三年的新论文，重点关注真实工具调用、MCP/函数调用和失败恢复`

重点检查：

- 论文同时覆盖 agent、tool/function calling、evaluation/benchmark。
- 追问后 source trace 能看到补搜或检索策略变化。
- 不出现泛 AI Agent 论文冒充工具使用评测。
- graph 不应全是无依据强关系。

历史坑：

- 搜出来全是 seed 保底论文。
- 追问“近三年”后没有新检索。
- 引用数未知被显示为 `0`。
- 演进图全是 `related` 或关系过度自信。

### C2：大模型多模态融合

首轮主题：

`大模型多模态融合`

追问：

`补充近三年的新论文，重点关注融合架构、跨模态对齐和缺失模态鲁棒性`

重点检查：

- query decomposition 能拆出三个 focus facets。
- 核心论文不应混入电池、无关公共数据集、软件工程 Agent 等跑题论文。
- 追问结果必须体现近三年和三个重点方向。
- taxonomy 分支数量与分支匹配论文展示一致。

历史坑：

- 追问后仍只用首轮 PDF 或旧论文。
- 搜到电池、表格检索、公共数据集可访问性等擦边论文。
- 演进图只有两篇论文，但论文池实际不止两篇。

### C3：AI Agent for Software Engineering

首轮主题：

`AI Agent for software engineering`

追问：

`缩小到近两年的代码 Agent 评测论文`

重点检查：

- 年份约束应进入检索计划。
- 代码 Agent、软件工程和评测三个概念都应被覆盖。
- 本次结果应区别于本研究总览。
- 总览不能只保留最新一轮，丢掉早期高价值论文。

历史坑：

- 追问缩小年份后没有补搜。
- summary 说“未覆盖某方向”，但用户正是在继续展开这个方向。
- 总览核心论文合并过度偏向最新一轮。

### C4：PDF + 混合研究

首轮设置：

- 研究主题：`大模型多模态融合`
- 研究方式：`导入 + 补搜`
- 先导入 2 至 5 篇本地 PDF

追问：

`在已有论文基础上补充近三年的系统检索论文`

重点检查：

- 用户上传 PDF 应显示为用户来源。
- hybrid 模式下不能只使用导入论文，也不能忽略导入论文。
- 追问应补充系统检索论文。
- 图谱和 taxonomy 应能同时使用导入论文与系统论文。

历史坑：

- 系统只在用户上传论文里重排。
- 用户导入论文元数据覆盖系统论文元数据。
- 引用数和来源身份在总览里丢失。

### C5：共享知识污染边界

准备：

- 在共享知识中放入一个与当前主题无关但语义上有“agent / benchmark”等泛词的历史结果。

首轮主题：

`大模型多模态融合`

知识范围：

`当前研究 + 全局`

重点检查：

- 无关共享知识可以被过滤或标为低相关。
- 即使命中，也只能作为上下文提示，不能进入论文证据。
- gaps / ideas 的 `supporting_paper_ids` 只能来自当前分析论文池。
- 前端命中知识区域不应让用户误以为它证明了结论。

历史坑：

- AI Agent for Software Engineering 的共享知识污染多模态研究。
- 命中知识展示抽象，用户看不懂为什么被用上。

### C6：Skill 与上下文链路

首轮设置：

- 新增一个 Skill，例如 `literature_review_matrix`。
- 勾选该 Skill 后创建研究。

重点检查：

- Skill 能创建、启停、选择并持久化。
- 依赖不存在或关闭的工具时有明确错误或提示。
- 任务 trace 中记录 `selected_skill_ids`。
- Skill 只影响研究上下文，不应绕过论文证据规则。

历史坑：

- 文档写了 Skill，但实际不能新增或选择。
- Skill 描述进入上下文后，可能被误当作论文证据。

### C7：大模型多模态搜索 + 导入论文混合链路

首轮设置：

- 研究主题：`基于大模型的多模态搜索`
- 研究方式：`导入 + 系统搜索`
- 可导入 2 至 5 篇本地多模态检索 / 跨模态检索相关 PDF

追问：

`补充近三年的系统检索论文，重点关注多模态检索失败模式、跨模态对齐和可扩展检索架构`

重点检查：

- 系统检索论文和用户导入论文都应进入证据池，但必须标清来源。
- 追问应补搜新论文，不能只在首轮导入论文里重排。
- Overview 研究简报应说明当前主题整体进展、主要路线、证据覆盖和下一步动作。
- 研究空白、研究建议、演进图节点和关系详情中不应出现裸 hash / opaque paper id，例如 `facd...`、`c48d...`。
- 研究建议的证据标签应区分 `直接证据 / 间接支撑 / 待验证假设`，不要把几乎所有建议都粗暴显示成“探索性方向”。
- Context / RAG 命中区域默认展示用途、来源、影响范围和证据边界，不应把原始 chunk、公式或内部拼接片段作为主内容展示。
- Agent DAG 图中的节点次数和边次数不能遮挡节点名称、状态和路径；如果图太密，应在右侧列表汇总。

历史坑：

- 研究空白支撑论文里出现内部 paper id。
- 演进图节点显示长 hash，而不是论文标题或“未识别论文”。
- RAG 命中片段像日志，用户无法理解它为什么被使用。
- 研究简报只复述覆盖方向，缺少领域进展判断，且被省略号截断。
- Agent 运行图的 `x2/x3` 挤在圆形节点里，看不清。

## 6. 判定口径

### 通过

- 没有触发全局红线。
- 至少一个追问体现新增检索或明确解释无新增原因。
- 核心论文整体相关。
- 结论证据边界清楚。
- 总览能体现多轮沉淀。

### 不通过

- 触发任一全局红线。
- 结果看似丰富但论文明显跑题。
- 用户追问约束没有进入检索计划。
- 强关系或研究建议缺乏证据。

### 需复测

- 外部数据源临时不可用。
- 论文数量偏少，但系统明确展示证据不足。
- 模型输出质量波动，需要再次运行确认。

## 7. 下一步自动化方向

短期仍以人工验收为主，但结构化用例已经预留自动化字段。后续可以逐步自动检查：

- workspace JSON 中 `source_trace.refresh_triggered`。
- `novel_paper_count` 和 `reused_paper_count`。
- `citation_count_known` 与前端显示。
- `gaps[*].evidence_level` 和 `supporting_paper_ids`。
- `graph_edges[*].relationship` 的类型分布。
- taxonomy 分支 `matched_paper_ids` 与前端展示一致性。
- 用户可见文本中是否包含长 hash、`focus:`、`title:` 等内部调试串。
- research brief 是否包含整体进展、证据覆盖和下一步动作。
