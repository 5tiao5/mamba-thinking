# 迭代三架构设计说明 v1

## 1. 设计目标

本版本架构设计的目标是：

- 在不破坏旧版原型的前提下，为迭代三建立新的工程骨架
- 明确系统分层、模块边界和依赖方向
- 让组员可以围绕固定接口并行开发
- 先冻结“结构”，再逐步补齐“实现”

这份设计强调工程思维，重点不是某个单点功能，而是：

- 系统如何拆层
- 数据如何流动
- 模块如何协作
- 哪些能力属于 Agent 内核，哪些能力属于产品层

## 2. 总体架构

系统建议分为五层：

```text
UI Layer
    ↓
API Layer
    ↓
Application Service Layer
    ↓
Agent Core Layer
    ↓
Infrastructure Layer
```

### 2.1 UI Layer

职责：

- 承接用户输入
- 展示多轮对话
- 展示研究工作台
- 展示历史会话、工具配置和技能配置

本层不直接操作数据库，也不直接调用外部工具，只通过 API 访问系统能力。

### 2.2 API Layer

职责：

- 定义对外接口
- 校验请求参数
- 调用服务层
- 返回统一响应结构

本层不实现复杂业务逻辑。

### 2.3 Application Service Layer

职责：

- 组织产品级业务流程
- 协调会话、任务、知识、工具和技能
- 负责“一个功能要怎么完成”

例如：

- 创建会话
- 发送消息
- 启动研究任务
- 导出工作台结果
- 切换工具开关

### 2.4 Agent Core Layer

职责：

- 完成 Agent 本体的推理和任务执行
- 包括 controller、nodes、runtime、memory、evaluation

这一层负责“Agent 是怎么工作的”。

### 2.5 Infrastructure Layer

职责：

- 数据持久化
- 外部工具接入
- RAG / 共享知识支持
- 观测能力

这一层负责“系统怎么接外部世界、怎么存东西”。

## 3. 依赖方向

必须保持单向依赖：

- UI 依赖 API
- API 依赖 Services
- Services 依赖 Agent / Repositories / Registries
- Agent 依赖 Tools / Observability
- Repositories / Tools 属于基础设施

严禁出现：

- Agent 直接依赖 UI
- Repository 依赖 Service
- Tool 层依赖 API

## 4. 关键模块

## 4.1 会话域

负责：

- Conversation
- Message
- 多轮上下文
- 历史会话恢复

核心对象：

- `Conversation`
- `MessageRecord`
- `ConversationSummary`

## 4.2 研究任务域

负责：

- 一次研究分析任务的完整生命周期
- 检索、taxonomy、graph、gap、ideas 等结构化结果

核心对象：

- `ResearchTask`
- `ResearchWorkspace`
- `PaperRecord`
- `GapRecord`
- `ResearchIdeaRecord`

## 4.3 工具与技能域

负责：

- Tool Registry
- Skill Registry
- 工具配置
- 技能启用/禁用

核心对象：

- `ToolDescriptor`
- `SkillDescriptor`

## 4.4 知识共享域

负责：

- 历史研究成果沉淀
- 跨对话复用
- 后续 RAG 接入

核心对象：

- `KnowledgeDocument`
- `KnowledgeChunk`

## 4.5 评估域

负责：

- bad case 存档
- 优化前后结果记录
- 评估样本和运行结果

## 5. 关键设计原则

### 5.1 会话与研究任务分离

一次对话不等于一次任务。

建议拆成：

- `Conversation`
  - 用户和 Agent 的多轮聊天容器
- `ResearchTask`
  - 在某一时刻发起的一次分析任务

同一个会话中，用户可以触发多个任务。

### 5.2 产品状态与 Agent 状态分离

当前原型的 `ResearchState` 更像 Agent 运行时状态。

迭代三建议把状态拆成：

- 产品态：会话、消息、工作台快照
- 任务态：论文、taxonomy、graph、gap
- 运行态：thought trace、action history、tool events

### 5.3 对外接口与内部实现分离

所有面向 UI 的接口统一由 API 层定义，不让前端直接感知内部 Agent 状态结构。

### 5.4 仓储接口优先

先定义 Repository 接口，再决定具体数据库实现。

这样后续切换 SQLite / PostgreSQL / JSON 文件都不会影响业务层。

### 5.5 Tool / Skill 统一注册

不要在业务代码里散落地 import 工具并直接调用。

所有工具和 skill 都应走 registry 层，统一管理：

- 名称
- 描述
- 参数
- 开关
- 可用性

## 7. 典型调用链

### 用户发起一轮新研究任务

```text
UI -> API Handler -> ConversationService
   -> ResearchService
   -> Agent Pipeline
   -> ResearchWorkspace
   -> Repository Persist
   -> API Response
   -> UI Render
```

### 用户在已有会话中继续追问

```text
UI -> API Handler -> ConversationService
   -> WorkspaceService / KnowledgeService
   -> ResearchService
   -> Agent Pipeline (with context)
   -> Persist + Return
```

## 8. 组员开发约束

1. 业务逻辑优先写在 `services/`
2. Agent 运行逻辑优先写在 `research_agent/`
3. 数据访问优先走 `repositories/`
4. 工具与技能配置优先走 `registries/`
5. 面向前端的输入输出结构统一放在 `schemas/`

## 9. 这一版为什么是工程化的

因为它已经明确了：

- 分层
- 边界
- 依赖方向
- 数据契约
- 团队协作入口

后面哪怕某些技术栈变化，例如：

- FastAPI 或 Flask
- SQLite 或 PostgreSQL
- 本地文件或对象存储

都不会推翻这套结构。
