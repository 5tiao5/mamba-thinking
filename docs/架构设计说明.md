# 架构设计说明

这份文档回答两个问题：

1. 当前 `product_agent/` 是怎么分层的
2. 下一阶段开发时，哪些边界不能乱动

---

## 1. 当前设计目标

这一版架构的目标不是“所有功能一次性做完”，而是先保证：

- 目录结构清晰
- 分层边界清晰
- 接口合同稳定
- 主链路能跑
- 可以多人并行开发

换句话说：

**先把承重墙搭好，再让功能往里长。**

---

## 2. 当前总体分层

系统按五层组织：

```text
UI Layer
  -> API Layer
  -> Application Service Layer
  -> Agent Core Layer
  -> Infrastructure Layer
```

### 2.1 UI Layer

职责：

- 承接用户输入
- 展示首页、对话页、工作台、历史页、设置页
- 只通过 HTTP API 调用系统能力

代表目录：

- [ui/](/D:/iteration_two-master/iteration_two-master/product_agent/ui)

不应该做：

- 直接理解旧版 Agent state
- 自己计算后端业务状态
- 绕过 API 猜测数据结构

### 2.2 API Layer

职责：

- 定义对外接口
- 校验请求参数
- 调 service
- 返回统一响应

代表文件：

- [fastapi_app.py](/D:/iteration_two-master/iteration_two-master/product_agent/api/fastapi_app.py)
- [handlers.py](/D:/iteration_two-master/iteration_two-master/product_agent/api/handlers.py)

当前特点：

- 使用 `create_app()` 工厂装配 FastAPI
- handler 不直接访问 repository

### 2.3 Application Service Layer

职责：

- 编排产品级业务流程
- 管理会话、消息、任务、工作台、工具、技能、知识

代表目录：

- [services/](/D:/iteration_two-master/iteration_two-master/product_agent/services)

关键模块：

- `ConversationService`
- `MessageService`
- `ResearchService`
- `WorkspaceService`
- `ToolService`
- `SkillService`
- `KnowledgeService`
- `taxonomy_grounding_service`

### 2.4 Agent Core Layer

职责：

- 运行研究分析主流程
- 管理 controller、pipeline、runtime 和 nodes

代表目录：

- [research_agent/](/D:/iteration_two-master/iteration_two-master/product_agent/research_agent)

关键节点：

- `planner`
- `searcher`
- `taxonomy`
- `evolution`
- `auditor`
- `corrector`
- `synthesizer`

### 2.5 Infrastructure Layer

职责：

- 数据持久化
- 外部工具接入
- 可观测性
- shared knowledge / RAG 基础能力

代表目录：

- [repositories/](/D:/iteration_two-master/iteration_two-master/product_agent/repositories)

当前状态：

- 开发默认 SQLite
- 测试环境可切 memory

## 3. 当前核心对象关系

当前产品模型最重要的关系是：

```text
Conversation
  -> Message (多条)
  -> ResearchTask (多条)
ResearchTask
  -> Workspace (一条快照)
```

这意味着：

- 一个 Conversation 代表持续研究会话
- 一次追问可能触发一个新的 ResearchTask
- 每个 ResearchTask 产出一个 Workspace

当前这条链已经基本打通，但产品体验上还可继续加强。

---

## 4. 当前主链路

### 4.1 创建会话

`UI -> API -> ConversationService -> ConversationRepository`

### 4.2 继续对话

`UI -> /conversations/continue -> Handler -> MessageService -> ResearchService.create_follow_up_task`

### 4.3 运行研究任务

`UI -> /research/tasks/{task_id}/run -> ResearchService.run_task -> research_agent.pipeline -> workspace_mapper -> WorkspaceRepository`

### 4.4 读取工作台

`UI -> /research/tasks/{task_id}/workspace -> WorkspaceService.get_workspace_snapshot`

---

## 5. 当前设计原则

### 5.1 Conversation 和 Task 要分离

原因：

- 多轮对话不等于单次分析任务
- 同一个 conversation 可以触发多个 task

### 5.2 产品状态和 Agent 状态要分离

原因：

- 旧版 `ResearchState` 不适合直接暴露给前端
- 前端应消费稳定的 workspace snapshot

### 5.3 Repository 负责“怎么存”，Service 负责“什么时候存”

这条原则现在已经落地：

- SQLite / memory 可以切换
- 上层业务不用改

### 5.4 Tool / Skill / Knowledge 统一收在服务层边界里

原因：

- 防止业务代码里到处乱 import
- 便于后续扩展配置、持久化和部署

---

## 6. 当前已经稳定的部分

可以视为当前阶段相对稳定的边界：

- FastAPI 接口层
- Conversation / Message / ResearchTask / Workspace 主对象
- SQLite 默认持久化
- workspace 生成与快照返回机制
- 前端页面骨架与 workspace 组件拆分

---

## 7. 当前还在持续演化的部分

这些地方后续仍然会继续改，但应在现有边界内演化：

- 搜索质量
- taxonomy 生成与 grounding
- graph 解释与可视化
- assistant 回答风格
- knowledge / RAG
- 部署与 CI/CD

---

## 8. 下一阶段的架构重点

接下来最值得继续强化的，不是再推倒重来，而是：

1. 搜索 -> taxonomy -> workspace 的证据链质量
2. 会话 -> 追问 -> task -> workspace 的用户体验闭环
3. knowledge / RAG 主链接入

---

## 9. 组员开发时必须遵守的边界

1. 前端只依赖 API 和 schema
2. handler 不直接碰 repository
3. service 负责编排，repository 负责存取
4. research_agent 专注分析，不直接掺页面逻辑
5. 新功能继续优先落在 `product_agent/`

---

## 10. 一句话总结

这套架构现在的定位是：

**已经具备多人并行开发条件的工程基线。**

下一阶段重点不是“再搭架子”，而是：

**在这套分层上继续把产品体验和核心能力做实。**
