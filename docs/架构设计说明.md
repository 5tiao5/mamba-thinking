# 架构设计说明

## 1. 设计目标

这一版架构的目标不是“把所有功能一次性写完”，而是先把团队协作最关键的几件事固定下来：

- 目录结构清晰
- 分层边界清晰
- 接口合同稳定
- 调用链统一
- 旧原型能力可以逐步迁移进来

换句话说，我们先搭好骨架，再往里面长肌肉。

## 2. 总体分层

系统按五层组织：

```text
UI Layer
  -> API Layer
  -> Application Service Layer
  -> Agent Core Layer
  -> Infrastructure Layer
```

### 2.1 UI Layer

职责：

- 承接用户输入
- 展示对话页、工作台、历史页、设置页
- 只通过 HTTP 接口使用系统能力

不应该做：

- 直接理解旧版 Agent state
- 直接访问数据库
- 直接调用 Python 内部 service

### 2.2 API Layer

职责：

- 定义对外接口
- 校验请求参数
- 调用 service
- 返回统一响应结构

实现入口：

- `product_agent/api/fastapi_app.py`
- `product_agent/api/handlers.py`

当前设计重点：

- 使用 `create_app()` 工厂函数装配 FastAPI
- handler 只接参数、调 service、包响应
- handler 不直接访问 repository

### 2.3 Application Service Layer

职责：

- 编排产品级业务流程
- 协调会话、消息、任务、工作台、工具、技能、知识等模块
- 决定什么时候读写数据、什么时候运行 Agent

典型模块：

- `ConversationService`
- `MessageService`
- `ResearchService`
- `WorkspaceService`
- `ToolService`
- `SkillService`
- `KnowledgeService`

### 2.4 Agent Core Layer

职责：

- 执行研究分析主流程
- 管理 controller、nodes、runtime、pipeline

一句话理解：

这一层回答的是“Agent 本体怎么工作”。

### 2.5 Infrastructure Layer

职责：

- 数据持久化
- 外部工具接入
- 日志与可观测性
- shared knowledge / RAG 的基础能力

一句话理解：

这一层回答的是“系统怎么连外部世界、怎么存东西”。

## 3. 依赖方向

必须保持单向依赖：

- UI 依赖 API
- API 依赖 Services
- Services 依赖 Agent / Repositories / Registries
- Agent 依赖共享工具与可观测性模块
- Repositories / Registries / Tools 属于基础设施

严禁出现：

- Agent 直接依赖 UI
- Repository 依赖 Service
- Handler 直接访问 Repository
- 前端直接理解旧版 Agent 的内部状态

## 4. 关键设计原则

### 4.1 会话和任务分离

一轮对话不等于一轮任务。

- `Conversation` 管多轮聊天
- `ResearchTask` 管某次具体分析

同一个会话可以触发多个任务，尤其是 follow-up task。

### 4.2 产品状态和 Agent 状态分离

不要把旧原型 `ResearchState` 直接暴露给前端。

应该拆成：

- 产品态：会话、消息、工作台快照
- 任务态：papers、taxonomy、graph、gaps、ideas
- 运行态：thought trace、action history、tool events

### 4.3 Repository 优先

先定义仓储接口，再决定数据库实现。

也就是说：

- repository 负责“怎么存、怎么取”
- service 负责“什么时候存、什么时候取、为什么这么存”

这样后面无论接 SQLite、PostgreSQL 还是 JSON 文件，都不会反过来打碎业务层。

### 4.4 Tool / Skill 统一注册

工具和 skill 不应该散落在业务代码里直接 import 后乱调。  
统一通过 registry 管理：

- 名称
- 描述
- 参数
- 开关
- 配置

## 5. 目录结构

```text
product_agent/
├── api/
├── services/
├── repositories/
├── registries/
├── schemas/
├── domain/
├── research_agent/
├── ui/
├── docs/
├── app_container.py
└── main.py
```

每层职责：

- `api/`: 对外接口
- `services/`: 产品业务编排
- `repositories/`: 数据读写边界
- `registries/`: tool / skill 管理
- `schemas/`: 前后端合同
- `domain/`: 领域实体
- `research_agent/`: 分析引擎
- `ui/`: Web 前端

## 6. 当前主链路

### 6.1 创建会话

`UI -> FastAPI route -> ProductApiHandlers -> ConversationService -> ConversationRepository`

### 6.2 继续对话并创建 follow-up task

`UI -> /conversations/continue -> Handler -> MessageService -> ResearchService.create_follow_up_task -> TaskRepository`

### 6.3 运行研究任务

`UI -> /research/tasks/{task_id}/run -> Handler -> ResearchService.run_task -> research_agent.pipeline -> workspace_mapper -> WorkspaceRepository`

### 6.4 读取工作台

`UI -> /research/tasks/{task_id}/workspace -> Handler -> WorkspaceService.get_workspace_snapshot -> WorkspaceRepository`

## 7. 当前真实状态

已经比较稳的部分：

- FastAPI 主接口骨架
- React + Vite 前端骨架
- 会话链路
- 消息链路
- follow-up task 链路
- 研究任务运行链路
- workspace 快照链路

还在持续收口的部分：

- 历史页接口
- 正式数据库持久化
- 更细的 workspace 字段合同
- 完整 shared knowledge / RAG
- `auditor` / `synthesizer` 继续拆成更细的内部能力

## 8. 给组员的约束

1. 前端只依赖 API 和 `schemas/`。
2. 业务逻辑优先写在 `services/`。
3. Agent 分析逻辑优先写在 `research_agent/`。
4. 数据存取统一走 `repositories/`。
5. 新功能优先收敛到 `product_agent/`，不要继续在旧原型目录堆实现。

## 9. 总结

这套架构现在的定位是：

**可运行、可分工、可持续演化的工程基线版本。**

它已经足够支撑组员开工，但仍然保留了后续继续收紧字段、接数据库、补 RAG 的空间。
