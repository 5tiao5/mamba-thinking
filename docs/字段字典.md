# 字段字典

这份文档用于统一当前 `product_agent/` 的核心数据对象含义。

适用场景：

- 前端同学不知道某个字段是干嘛的
- 后端同学不确定某个字段该在哪一层使用
- 组长 review 时想快速判断字段有没有漂移

## 1. Domain 层对象

这些对象定义在：

- [entities.py](/D:/iteration_two-master/iteration_two-master/product_agent/domain/entities.py)

它们更偏系统内部业务对象，不一定和前端返回结构一模一样。

### 1.1 `Conversation`

| 字段 | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `conversation_id` | `str` | 会话唯一标识 | 前后端共用主键 |
| `title` | `str` | 会话标题 | 可由用户给定，也可从 topic 派生 |
| `topic` | `str` | 会话主研究主题 | 一个 conversation 的主线 |
| `status` | `str` | 会话状态 | 当前通常为 `active` |
| `message_ids` | `List[str]` | 消息 ID 列表 | 用于会话和消息关联 |
| `latest_task_id` | `Optional[str]` | 最近任务 ID | 历史页和工作台跳转会用到 |
| `created_at` | `datetime` | 创建时间 | 后端内部使用 |
| `updated_at` | `datetime` | 更新时间 | 后端内部使用 |

### 1.2 `MessageRecord`

| 字段 | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `message_id` | `str` | 消息唯一标识 | 消息主键 |
| `conversation_id` | `str` | 所属会话 ID | 与 `Conversation` 关联 |
| `role` | `str` | 消息角色 | `user / assistant / system` |
| `content` | `str` | 消息正文 | 当前对话主内容 |
| `metadata` | `Dict[str, Any]` | 扩展信息 | 可放 focus、task link、来源说明 |
| `created_at` | `datetime` | 创建时间 | 排序与时间线展示 |

说明：

- 当前 assistant message 已经会写回任务运行结果
- 但后续仍可继续增强，让它更像自然回复而不是日志摘要

### 1.3 `ResearchTask`

| 字段 | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `task_id` | `str` | 任务唯一标识 | 分析任务主键 |
| `conversation_id` | `str` | 所属会话 ID | 一个会话下可有多个任务 |
| `topic` | `str` | 本次任务分析主题 | 可与 conversation topic 相同或更细 |
| `status` | `str` | 任务状态 | `created / running / completed / failed` |
| `trigger_message_id` | `Optional[str]` | 触发该任务的消息 ID | follow-up task 重要关联点 |
| `mode` | `str` | 运行模式 | 当前支持 `default / fast / balanced` |
| `created_at` | `datetime` | 创建时间 | 历史记录使用 |
| `updated_at` | `datetime` | 更新时间 | 状态流转使用 |

### 1.4 `PaperRecord`

| 字段 | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `paper_id` | `str` | 论文唯一标识 | 当前常用 arXiv id 或 fallback id |
| `title` | `str` | 论文标题 | 前端建议以英文原文为主 |
| `abstract` | `str` | 摘要 | 用于 workspace、taxonomy grounding、search |
| `authors` | `List[str]` | 作者列表 | 当前可简化展示 |
| `keywords` | `List[str]` | 关键词 | 当前主要给 taxonomy grounding 与后端分析服务使用 |
| `publish_date` | `str` | 日期 | 当前先保留字符串 |
| `source` | `str` | 来源 | 例如 `arxiv / fallback` |
| `taxonomy_category` | `str` | 论文分类标签 | 当前既用于显示，也用于 grounding 辅助 |
| `citation_count` | `int` | 引用数 | 当前常为近似值或默认值 |
| `url` | `Optional[str]` | 论文链接 | 前端打开来源用 |

说明：

- `source = fallback` 不代表真实数据库来源
- 它表示系统在检索证据不足时使用了保底 seed paper

### 1.5 `ResearchWorkspace`

| 字段 | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `task_id` | `str` | 对应任务 ID | 一个 task 产出一个 workspace |
| `topic` | `str` | 当前研究主题 | 工作台主标题来源 |
| `summary` | `str` | 面向用户的摘要 | 已兼容旧 summary 清洗 |
| `summary_payload` | `Dict[str, Any]` | 结构化摘要信息 | 更适合后续稳定展示 |
| `papers` | `List[PaperRecord]` | 论文证据 | 工作台主证据区 |
| `taxonomy` | `Dict[str, Any]` | taxonomy 结构 | 已经接入 grounding 服务 |
| `graph_edges` | `List[Dict[str, Any]]` | 论文关系边 | 演进图谱与关系明细 |
| `gaps` | `List[Dict[str, Any]]` | 研究空白 | 洞察区 |
| `ideas` | `List[Dict[str, Any]]` | 研究建议 | 洞察区 |
| `alignment_score` | `float` | 匹配度 | 前端摘要与总览区使用 |
| `trace` | `List[Dict[str, Any]]` | 过程信息 | 当前主要用于解释和调试 |

## 3. 当前 taxonomy 相关字段应该怎么理解

这是当前最容易被误解的一块。

### `paper_count`

意思：

- 当前被归因到该 taxonomy branch 的论文数

注意：

- 它不是简单数“这个分支名有没有出现在论文标题里”
- 当前已经由 `taxonomy_grounding_service.py` 综合 branch name、description、required concepts，以及论文 title / abstract / keywords / taxonomy_category 去计算
- 新一轮后端改动里，宽问题还会先经过 query decomposition，再把检索回来的论文证据喂给 taxonomy，所以 `paper_count` 更接近“证据归因结果”，而不是“标题碰词结果”

### `coverage`

意思：

- 当前论文证据对该分支的覆盖程度

常见情况：

- `0.00`：当前没有有效覆盖，通常也会看到 `0篇`
- 低分：有少量边缘证据
- 高分：该 branch 已有较强文献支撑
- 它本质上反映的是“证据覆盖度”，不是 taxonomy 自己想象出来的完整性

### `gap_count`

意思：

- 当前被归因到该 branch 的研究空白数量

### `matched_paper_ids`

意思：

- 哪些论文被 grounding 到该 branch

这个字段当前主要给后端和调试用，前端可按需使用，不必强依赖。

## 4. 当前 graph 相关字段应该怎么理解

### `graph_edges[*].source_paper_id`

关系边起点论文 ID

### `graph_edges[*].target_paper_id`

关系边终点论文 ID

### `graph_edges[*].relation`

关系类型，例如：

- `improves`
- `references`
- `compares`

### `graph_edges[*].evidence`

为什么会生成这条边的解释

### `graph_edges[*].weight`

当前边强度或置信度的近似值

说明：

- 前端图谱展示可以继续增强，但不应该自己生成关系
- 图是数据解释，不是数据来源

## 5. 当前 knowledge / RAG 相关字段状态

### 已有

- `knowledge_documents`
- `summary`
- 基础检索服务

### 还缺

- 用户可感知的知识导入入口
- 主链路中的显式知识召回结果
- assistant 回复中引用知识来源

所以现在如果组员看到 `KnowledgeService`，应该理解为：

**“知识层基础设施已在，但产品级 RAG 还未闭环。”**

---

## 6. 一句话总结

当前最重要的字段关系可以记成：

- `Conversation` 管长期研究会话
- `MessageRecord` 管多轮交流内容
- `ResearchTask` 管单次分析动作
- `ResearchWorkspace` 管单次分析结果

而 `taxonomy / graph / gaps / ideas` 则是：

**Workspace 里的结构化研究结果，不应在前端被重新发明一遍。**
