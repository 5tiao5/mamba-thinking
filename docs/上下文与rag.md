# 上下文与 RAG 设计说明

## 1. 为什么现在就要说明这件事

因为迭代三的关键能力不只是“跑一次 Agent”，而是：

- 支持多轮对话
- 支持跨对话知识共享
- 支持后续 RAG 知识增强

如果这三件事不先在架构和注释里讲清楚，组员在实现时很容易出现：

- 上下文理解各做各的
- 知识共享和会话历史混在一起
- RAG 直接写死在业务函数里

所以当前阶段虽然可以不急着把 RAG 全实现，但必须先把设计逻辑和接口边界定下来。

## 2. 上下文分哪几类

建议把上下文分成三层：

### 2.1 当前轮输入

来源：

- 用户当前输入的消息

作用：

- 决定本轮问题的直接目标

### 2.2 会话级上下文

来源：

- 当前 conversation 的历史消息
- 对历史消息做摘要后的 conversation summary

作用：

- 让 Agent 知道用户之前讨论过什么
- 支持多轮追问

### 2.3 外部知识上下文

来源：

- 历史任务沉淀下来的知识文档
- 后续知识库检索结果

作用：

- 复用过往研究结果
- 提高回答一致性和效率

## 3. 推荐的上下文处理策略

### 第一阶段：只做会话摘要

适合当前最小可用实现。

做法：

- 最近几条消息直接保留
- 更早消息压缩成一段 summary
- 本轮调用 Agent 时一并带入

### 第二阶段：加入知识检索

做法：

- 根据当前 topic / focus 检索历史知识文档
- 取相关知识片段作为 retrieved_knowledge
- 传给 planner / synthesizer / compare 等模块

### 第三阶段：上下文治理

做法：

- 限制传入上下文总长度
- 记录本轮实际用到的上下文来源
- 提供引用或出处标记

## 4. RAG 在这个项目里应该怎么理解

这里的 RAG 不要理解成“必须马上上一个很复杂的向量平台”。

在你们项目里，RAG 更实际的意思是：

`从历史沉淀的研究知识中，把本轮最相关的信息检索出来，再提供给 Agent 使用。`

它的本质目的是：

- 复用已有研究结果
- 避免每次都从零开始
- 提高多轮对话和跨会话的一致性

## 5. 当前推荐的 RAG 路线

### 阶段 A：结构化知识复用

暂时不用向量库。

先保存：

- topic
- report summary
- taxonomy summary
- representative papers
- gap summary

再按关键词和 tag 做初步检索。

### 阶段 B：chunk + embedding

当结构化知识复用稳定后，再做：

- 文档切块
- embedding 生成
- 向量检索

### 阶段 C：混合检索

最终再考虑：

- 关键词过滤
- 向量召回
- rerank

## 6. 为什么可以把数据库放后面

因为上下文和 RAG 现在最重要的是先定：

- 数据结构
- 服务接口
- 调用链路

具体的持久化实现可以后接。

当前可以先用：

- InMemory repository
- 文件存储

后续再换成：

- SQLite
- PostgreSQL
- PostgreSQL + pgvector

只要 repository 和 service 接口先定好，就不会影响整体架构。

## 7. 组员实现时要遵守什么

1. 会话历史不要直接散落在 handler 或 UI 中管理
2. 上下文摘要逻辑优先放在 service 或专门的 context 模块
3. RAG 检索入口统一走 KnowledgeService
4. 不要在单个节点里私自写死知识检索逻辑
5. 所有被注入 Agent 的上下文，最好都能记录来源

## 8. 结论

当前阶段最合理的做法是：

- 先把上下文和 RAG 的“接口和职责”定清楚
- 暂时不急着把完整向量检索全落地
- 先从会话摘要和结构化知识复用做起

这样既符合工程推进节奏，也不会把组员实现拖进过早的基础设施细节。
