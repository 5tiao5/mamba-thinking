# 主链路时序图

本文档只讲当前最关键的两条链路：

1. `创建会话 -> 创建任务 -> 运行任务 -> 读取 workspace`
2. `继续对话 -> 写消息 -> 创建 follow-up task -> 回写 assistant 回复`

这份文档的作用不是装饰，而是帮助组员在开发时想清楚：

- 用户点一次按钮后，系统到底做了哪些事
- 哪一层该做什么
- 哪一层不该越界

---

## 1. 主链路一：创建任务并读取工作台

```mermaid
sequenceDiagram
    participant U as User
    participant FE as Frontend
    participant API as FastAPI Route
    participant H as ProductApiHandlers
    participant CS as ConversationService
    participant RS as ResearchService
    participant AG as research_agent.pipeline
    participant WM as workspace_mapper
    participant WR as WorkspaceRepository
    participant WS as WorkspaceService

    U->>FE: 输入 topic 并创建会话
    FE->>API: POST /conversations
    API->>H: create_conversation(request)
    H->>CS: create_conversation(topic, title)
    CS-->>H: Conversation
    H-->>API: ApiResponse
    API-->>FE: conversation_id

    U->>FE: 创建研究任务
    FE->>API: POST /research/tasks
    API->>H: create_research_task(request)
    H->>RS: create_task(conversation_id, topic, mode)
    RS-->>H: ResearchTask
    H-->>API: ApiResponse
    API-->>FE: task_id

    U->>FE: 运行研究任务
    FE->>API: POST /research/tasks/{task_id}/run
    API->>H: run_research_task(task_id)
    H->>RS: get_task(task_id)
    RS-->>H: ResearchTask
    H->>RS: run_task(task)
    RS->>AG: run_pipeline(topic)
    AG-->>RS: agent state
    RS->>WM: workspace_from_agent_state(task_id, topic, state)
    WM-->>RS: ResearchWorkspace
    RS->>WR: save(workspace)
    WR-->>RS: saved
    RS-->>H: run result
    H-->>API: ApiResponse
    API-->>FE: task summary

    FE->>API: GET /research/tasks/{task_id}/workspace
    API->>H: get_workspace(task_id)
    H->>WS: get_workspace_snapshot(task_id)
    WS->>WR: get_by_task(task_id)
    WR-->>WS: ResearchWorkspace
    WS-->>H: WorkspaceSnapshotResponse
    H-->>API: ApiResponse
    API-->>FE: workspace snapshot
```

## 2. 主链路二：继续对话并触发 follow-up task

```mermaid
sequenceDiagram
    participant U as User
    participant FE as Frontend
    participant API as FastAPI Route
    participant H as ProductApiHandlers
    participant CS as ConversationService
    participant MS as MessageService
    participant RS as ResearchService
    participant WR as WorkspaceRepository

    U->>FE: 在 Conversation 中继续追问
    FE->>API: POST /conversations/continue
    API->>H: continue_conversation(request)
    H->>CS: get_conversation(conversation_id)
    CS-->>H: Conversation
    H->>MS: create_message(user message)
    MS-->>H: MessageRecord
    H->>MS: get_recent_context(conversation_id)
    MS-->>H: context_preview
    H->>RS: create_follow_up_task(...)
    RS-->>H: ResearchTask
    H-->>API: ApiResponse
    API-->>FE: message + context_preview + follow_up_task

    U->>FE: 运行 follow-up task
    FE->>API: POST /research/tasks/{task_id}/run
    API->>H: run_research_task(task_id)
    H->>RS: run_task(task)
    RS-->>H: run result
    H->>MS: create_assistant_message(...)
    MS-->>H: assistant message saved
    H-->>API: ApiResponse
    API-->>FE: task summary
```

## 3. 这两条链路里每层各负责什么

### Frontend

负责：

- 发请求
- 显示结果
- 管理页面状态

不负责：

- 直接拼 taxonomy coverage
- 直接理解旧版 agent state
- 跨过 API 去猜后端内部结构

### FastAPI Route + Handler

负责：

- 接参数
- 调 service
- 返回统一响应

不负责：

- 直接写 SQL
- 直接改 repository 内部状态
- 直接手搓复杂分析逻辑

### Service

负责：

- 编排业务逻辑
- 决定什么时候创建消息、什么时候创建任务、什么时候保存 workspace

不负责：

- 页面展示
- 直接承担图形渲染含义

### research_agent

负责：

- 真正跑分析流程
- 产出 agent state

不负责：

- 直接生成前端页面结构

### Repository

负责：

- 持久化 conversation / message / task / workspace / knowledge

不负责：

- 决定业务流程

## 4. 当前已经打通的部分

已经真实打通：

- 创建会话
- 创建任务
- 运行任务
- 读取 workspace
- 继续对话
- follow-up task 创建
- assistant 任务结果回写消息
- SQLite 持久化

也就是说：

**Conversation -> Message -> ResearchTask -> Workspace**  
这条关系链在后端数据层面已经成立。

---

## 5. 当前还没完全闭环的部分

### 5.1 Conversation 体验还不像完整研究会话

虽然 assistant message 已经会回写，但现在更多还是“任务摘要”，还不够像一段自然回答。

### 5.2 Knowledge / RAG 还没真正插进主链

现在的主链路仍主要依赖：

- 当前用户输入
- 最近会话消息
- 外部检索结果

而不是：

- 历史知识沉淀
- 用户导入论文
- 检索增强知识片段

### 5.3 Workspace 仍偏“结果面板”

还需要继续往：

- 更自然的阅读顺序
- 更强的图谱解释
- 更清晰的 taxonomy / graph 联动

方向优化。

---

## 6. 组员实现时最容易踩的坑

1. 在前端自己重算 coverage 或 gap 数
2. 在 handler 里直接访问 repository
3. 在某个页面里直接假设 task 一定已经完成
4. 在 `continue_conversation` 里只写用户消息，不回写 assistant 结果
5. 把 `KnowledgeService` 当成“已经完整接入 RAG”

---

## 7. 一句话总结

当前系统主链路已经从“页面占位”走到了：

**可创建会话、可发追问、可触发任务、可保存结果、可读取工作台的真实工程链路。**

下一阶段重点不再是“有没有链路”，而是：

**让这条链路更自然、更稳定、更像真正的持续研究助手。**
