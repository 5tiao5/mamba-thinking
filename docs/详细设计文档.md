# 详细设计文档

更新时间：2026-06-18

## 1. 总体设计

Product Agent 采用前后端分离架构。前端负责用户输入、状态展示和结果解释；后端负责任务编排、论文检索、知识检索、Agent 流程、证据审计和 workspace 聚合。

```text
React UI
  -> FastAPI API
  -> Services
  -> Research Agent Pipeline
  -> Repositories / Tools / Knowledge Index
```

更完整的架构边界见 [架构设计说明](架构设计说明.md)。

## 2. 分层职责

| 层级 | 代表目录 | 职责 |
| --- | --- | --- |
| UI Layer | `ui/` | 新建研究、对话追问、工作台展示、设置与知识导入 |
| API Layer | `api/` | FastAPI 路由、请求校验、统一响应 |
| Service Layer | `services/` | 会话、任务、工作台、知识、论文资产、Skill、运行配置 |
| Agent Core | `research_agent/` | planner/searcher/taxonomy/evolution/auditor/corrector/synthesizer |
| Repository Layer | `repositories/` | SQLite 与内存仓储 |
| Tool Layer | `tools.py`、`paper_content_tools.py` | arXiv、Semantic Scholar、PDF 内容处理、引用与元数据补全 |

## 3. 核心领域对象

### 3.1 Conversation

一个长期研究主题。用户围绕同一 Conversation 进行首轮研究和多轮追问。

### 3.2 Message

会话消息，记录用户输入和系统回复。追问消息可以触发 follow-up task。

### 3.3 ResearchTask

一次研究生成任务。首轮研究和每次追问都可以形成独立 ResearchTask。任务保存：

- topic
- mode
- knowledge_scope
- research_mode
- selected_skill_ids
- status

### 3.4 Workspace

一次任务或一个会话总览的结构化结果快照，包含：

- summary / research_brief
- papers
- taxonomy
- graph
- gaps
- ideas
- source_trace
- knowledge_hits
- working_memory

### 3.5 KnowledgeDocument

知识库文档。是否带 `conversation_id` 决定它是当前研究私有知识还是全局共享知识。

### 3.6 ConversationResearchPaper

当前研究论文池条目。用于区分用户上传论文、系统检索论文、核心论文和候选论文。

## 4. 主链流程

### 4.1 首轮研究

```text
用户新建研究
  -> 可选导入 PDF
  -> 创建 ResearchTask
  -> 运行 Agent Pipeline
  -> 写入 task events
  -> 生成 Workspace
  -> 回写 assistant message
  -> 前端刷新本次结果
```

### 4.2 追问研究

```text
用户发送追问
  -> 写入 user message
  -> 检索相关知识和历史 workspace hints
  -> 创建 follow-up ResearchTask
  -> 自动运行任务
  -> 轮询 task events
  -> 任务完成后刷新历史和 workspace
```

### 4.3 本研究总览

```text
读取同一 conversation 下已完成任务
  -> 聚合论文、taxonomy、graph、gaps、ideas
  -> 保留来源和证据等级
  -> 合并 working memory
  -> 输出 conversation workspace
```

## 5. Agent Pipeline 设计

当前 Agent 不是完全外部框架驱动，而是项目内手写的可控 pipeline。

| 节点 | 职责 |
| --- | --- |
| Planner | 理解研究主题、生成检索计划、合并知识线索 |
| Searcher | 多源检索、PDF/导入论文合并、相关性筛选、核心论文选择 |
| Taxonomy | 生成研究方向分类与分支证据 |
| Evolution | 构建论文关系图谱，区分引用、改进、扩展、互补、主题关联等关系 |
| Auditor | 审计 taxonomy、图谱、空白和建议的证据一致性 |
| Corrector | 针对证据不足或方向缺失做补搜和修正 |
| Synthesizer | 生成研究简报、空白、建议和最终 workspace bundle |

前端 Agent 运行图使用 task events 展示这些节点的运行过程。等待画板的设计原则是：用户可以看到系统正在推进，而不是只看到一个不可解释的 loading。

## 6. 检索与证据池设计

### 6.1 多源召回

系统支持：

- arXiv 搜索。
- Semantic Scholar 搜索和引用数补全。
- OpenAlex / arXiv 候选反查。
- 用户上传 PDF。
- 用户导入论文候选。

### 6.2 相关性分层

论文会被分成：

- direct：直接证据。
- adjacent：邻近证据。
- background：背景材料。
- rejected：低相关候选。

核心分析池不是简单取前 N 篇，而是综合：

- 主题相关性。
- 用户上传权重。
- 年份约束。
- 引用数或影响力。
- 与追问约束的匹配。
- 证据池多样性。

### 6.3 论文来源与元数据

每篇论文保留来源信息和引用数是否已知。引用数未知时前端显示“未获取”，不能显示为确定的 `0`。

## 7. RAG 与共享知识设计

知识范围有三种：

| scope | 语义 |
| --- | --- |
| `none` | 不使用知识库 |
| `conversation_only` | 只使用当前研究私有知识 |
| `shared` | 使用当前研究私有知识 + 全局共享知识 |

全局共享知识是不带 `conversation_id` 的 KnowledgeDocument；当前研究私有知识带 `conversation_id`。后端在检索时会过滤其他研究的私有文档，避免跨研究泄漏。

重要边界：

**知识命中只进入上下文，不自动成为论文证据。** 只有进入当前分析论文池的论文，才能支撑 taxonomy、graph、gaps 和 ideas。

## 8. 论文详情与 claim verification

论文详情目前分为三层：

1. 元数据：标题、来源、年份、分类、引用数、外链。
2. Paper Brief：研究问题、方法、贡献、局限、为什么先读。
3. Claim Checks：从摘要、正文片段或 PDF 解析内容中抽取可核查主张，标注 verified、partial、unknown 等状态。

当前已经具备正文片段级核查基础。后续可以继续演进为更完整的全文 claim verification，但必须控制运行时间和成本。

## 9. 前端页面设计

主要页面：

- 首页/新建研究入口。
- 对话页：研究会话、追问、可继续追问建议、Agent 运行画板。
- 工作台：Overview、Evidence、Map、Context、Run 分区。
- 设置页：工具、Skill、知识库。
- 历史页：研究记录与任务状态。

工作台分区设计：

| 分区 | 用户问题 |
| --- | --- |
| Overview | 这轮研究结论是什么？下一步做什么？ |
| Evidence | 论文证据有哪些？哪些值得先读？ |
| Map | 研究方向和论文关系如何组织？ |
| Context | 系统用了哪些上下文和知识？ |
| Run | Agent 运行过程中发生了什么？ |

- `POST /knowledge/documents`

## 11. 可扩展点

- 引入更强的多源论文检索。
- 将 Paper Analyst 并行化。
- 给 graph 强关系接入更完整的全文证据。
- 把 Skill 从策略模板扩展为更完整的可执行能力。
- 将 evaluation cases 接入 CI，形成质量门禁。
